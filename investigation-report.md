## 1. Executive Summary

On 2026-09-03/04, an alert was generated by Elastic Defend's Malware Prevention engine on host `ubuntu-elastic` following the download of a test file (`eicar.txt`) that matched the industry-standard EICAR test signature. The file was automatically quarantined/removed by the endpoint agent before it could be accessed. This investigation confirms the alert is a **true positive, expected result** of a planned detection-validation exercise — no malicious activity or actual threat was present. The purpose of this report is to document the detection pipeline's behavior end-to-end, as would be expected of a SOC analyst validating EDR efficacy after a new deployment.

**Outcome:** Detection and prevention controls performed as designed. No further remediation required. Finding closed as validated/expected.

## 3. Background & Scope

The EICAR test file is a non-malicious ASCII string that all reputable AV/EDR engines are designed to flag as if it were malware, allowing safe end-to-end validation of a detection stack without deploying live malicious code. This test was conducted deliberately to validate that a newly deployed Elastic Defend agent — enrolled via Fleet Server on a self-managed Elastic Stack — could actually detect and act on a threat, not just report a "healthy" status.

This is standard practice in SOC/detection-engineering work: a new sensor, agent, or rule is not considered production-validated until it has been exercised against a known-bad artifact and confirmed to alert and/or block correctly.

## 5. Analysis

**Detection mechanism:** Elastic Defend's Complete EDR tier includes signature and behavioral malware prevention in addition to telemetry collection. The EICAR string is a known static signature that any compliant AV/EDR engine recognizes; Elastic Defend flagged the file on a file-write/process event and took automatic prevention action (deletion) rather than only alerting.

**Why this matters for validation:** Many EDR misconfigurations manifest not as "no agent installed" but as an agent that is installed and reporting healthy while its prevention policy is silently set to detect-only, or its integration is misconfigured such that file execution events are not evaluated. This test rules that failure mode out — it confirms:
1. The agent is actively inspecting file activity, not just heartbeat-reporting.
2. The prevention policy is enforcing block/remove actions, not just logging.
3. Alert data is correctly reaching Kibana with accurate metadata (host, severity, risk score, reason codes).

**Process context:** The alert reason field (`file event with process context`) indicates Elastic Defend captured the responsible process (the shell invoking `curl`) alongside the file event — consistent with EDR-grade telemetry rather than simple AV file-scanning, and would allow an analyst to pivot to parent-process and command-line data in a real investigation.

**False positive consideration:** None. This was an intentional, controlled test using a purpose-built industry test string; there is no ambiguity in classification.

## 7. Response Actions Taken

- **Containment:** Not required — Elastic Defend auto-remediated by deleting the file at write time, before execution or further action was possible.
- **Verification:** Analyst independently confirmed file non-existence via filesystem check, cross-validated against the Kibana alert record.
- **Documentation:** Alert details (rule name, severity, risk score, host, reason) captured for the lab record.

---

## 8. Recommendations

1. **Expand validation coverage.** EICAR only proves signature-based file prevention. Follow-up tests should validate behavioral/process-based detections (e.g., a benign script simulating suspicious process trees, LOLBins usage, or Atomic Red Team test cases mapped to MITRE ATT&CK) to confirm behavioral prevention layers are equally effective.
2. **Tune alert routing.** Confirm this alert type would trigger a notification (email/Slack/webhook) in a production-like configuration, not just appear silently in the Kibana dashboard.
3. **Document detection coverage against MITRE ATT&CK.** As more test cases are run, map each to an ATT&CK technique ID to build a coverage matrix — this is a common SOC deliverable and strengthens the lab as a portfolio artifact.
4. **Retention/logging validation.** Confirm the underlying file and process events are retained in the Elasticsearch index (not just the derived alert) so a real investigation could pivot to raw telemetry.
5. **Multi-host testing.** Current validation covers a single host; if additional endpoints are enrolled, repeat this test on each to confirm consistent policy application across the fleet.

---

## 9. Conclusion

This investigation confirms that the Elastic Defend EDR deployment — including Fleet Server enrollment, agent health, and the Complete EDR policy tier — is functioning as designed. The EICAR test file was detected and automatically prevented within seconds of download, and the resulting alert was accurately surfaced in Kibana with correct severity, risk scoring, and contextual metadata. This closes out the initial detection-validation phase of the lab; the finding is expected/benign and requires no remediation beyond the coverage-expansion recommendations above.
